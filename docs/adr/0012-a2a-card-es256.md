# ADR-0012: Publish an A2A 1.0 agent card signed with ES256

**Status:** Accepted

## Context
An agent card is the JSON document an agent publishes so other agents know what it does and where
to reach it. The card here used the format from before Agent2Agent (A2A) 1.0: a top-level `url` and
`protocolVersion`, and a non-standard `x-authority` field. It was signed with HMAC, in which the
signer and every checker share one secret. Anyone able to check a card could therefore forge one.
Its canonical form came from a hand-written `json.dumps`, which differs from RFC 8785 on how
numbers are written.

## Decision
* The card lists its address under `supportedInterfaces`, with `protocolBinding` JSONRPC and
  `protocolVersion` 1.0, as A2A 1.0 requires.
* The no-refusal rule is published as a declared extension under `capabilities.extensions`, with
  `mayRecommendGrant` true and `mayIssueRefusal` false.
* The card is signed with ES256 through the `cryptography` package. The protected header is
  `{"alg": "ES256", "typ": "JOSE", "kid": ...}` and the signature is the raw 64-byte form JWS
  expects.
* The signed bytes are the card without its `signatures` field, in the canonical form produced by
  the `rfc8785` package.
* `verify_card` accepts a card only if a signature verifies against a public key the caller
  already trusts, named by its `kid`.

## Consequences
* Six tests cover the card's shape, a valid signature, reordered fields, a tampered extension, a
  wrong or unknown key, and an unsigned card.
* The tamper test found that `sign_card` copied the card shallowly, so editing a signed card
  changed the module's `CARD`. It now deep-copies.

## Open questions
* The key is generated at run time. Production needs a managed private key, a published public key
  (A2A allows a `jku` header pointing at one) and a rotation plan.
* A caller must already trust the key. How a calling agent learns which keys belong to this
  authority is not settled here.
